# 问题记录（踩坑 → 定位 → 修复 → 验证）

本项目从"跑通上游"到"可演示、可复现、有实验数据"的过程中，遇到的问题都在这里。
按来源分成三类：**用户提出的问题**（体验/产品视角，优先记录）、**工程实现中发现的问题**、
**环境与工具链问题**。每条都写了定位方式与验证结果——面试时可直接作为"排查故事"讲。

## 二、工程实现中发现的问题

| # | 问题 | 根因 | 修复 | 验证 |
| --- | --- | --- | --- | --- |
| E1 | 任务偶发"LLM调用失败：重试 5 次后仍失败" | 网络瞬时抖动 + 冷启动 | 指数退避重试（上限 16s）、启动预热 `warmup`、失败**不写入**长期记忆（防污染）、GUI 提供重试按钮 | 扫描 216 次中成功率 90%+；失败样本不再污染记忆库 |
| E2 | Bing HTML 解析结果不稳定/缺字段 | HTML 结构随请求变化，正则易漏 | 改用 Bing **RSS 输出**（`format=rss`，结构化稳定），HTML 解析作为兜底 | 同一查询 3/3 稳定返回；解析单测覆盖两种格式 |
| E3 | 长短语搜索返回无关结果（"诺坎普球场 参观" → 汉字"诺"字典页） | 搜索引擎对长短语分词退化 | 相关性过滤（中文 2-gram + 英文词匹配，剔除 0 分噪声并按分重排） | 单测 + 实测：5 条查询全部命中相关内容 |
| E4 | 自动缩短重试对"无空格长查询"无效 | 缩短逻辑把 5 字实体名也截断（"诺坎普球场"→"诺坎普球"） | 多段时取最长汉字段**不截断**；单段超长时先剥离后缀词（参观/攻略/开放时间…）再截断 | `_shorten_query` 单测（含 4 种形态） |
| E5 | 相关性过滤把无关结果判为相关 | 纯数字 token（如 "2026"）误匹配"诺兰电影 2026" | token 提取排除纯数字，英文词要求以字母开头 | 单测覆盖 |
| E6 | 模型把步数烧在检索上，最后只回一句"抱歉" | 无收口机制；模型不知道剩余预算 | 预算感知收口（剩 2 步提示收口、最后一步禁用工具）；摘要如实标注"达到步数上限仍未作答" | 同一任务 19 步产出完整方案 |
| E7 | **自动参数估计静默回退规则**（排查成本高） | `CountingLLM.chat` 只接受 dict 消息，`auto_budget` 传了 `Message` 对象 → `AttributeError` 被 `except` 吞掉，表现为"模型估计不可用" | ① 调用方改传 dict；② `config.py` 增加 `as_chat_message()` 归一化（兼容两种类型）；③ 失败时打印原因 | 修复后 `source=llm`；Message 对象兼容性也验证通过 |
| E8 | `budget_report.py` 报"没有找到 sweep 结果" | sweep JSON 顶层键是 `records` 而非 `results`（脚本猜错了键名），且提示信息误导 | 兼容 `records`/`results` 两种键；提示信息区分"无文件"与"无记录" | 脚本输出 216 次运行的完整统计 |
| E9 | 记忆库路径在 3 处重复定义（运行/清空/浏览器） | 复制粘贴式扩展 | 统一为 `ltm_path()` 单点定义 | 三处功能实测一致 |
| E10 | 模型每步并行调用 2–3 个工具，步数消耗快 | 模型倾向并行探索 | 用步数上限 + 收口提示治理（保留并行能力，因其能减少往返） | 观察项：研究型任务 20 步内可收敛 |
| E11 | 长任务上下文增长快（19.9k prompt tokens） | 每步把工具结果全量入上下文 | 记忆策略与预算裁剪已生效（`selection` 可见选中/总字符）；研究型任务仍建议控制抓取页数 | 面板可观测，文档记录边界 |
| E12 | 连续对话第 2 轮报错 `SQLite objects created in a thread can only be used in that same thread` | 每轮 `/api/run` 在新线程执行，而复用的会话持有上一线程创建的 SQLite 连接（LLM 客户端同样有跨事件循环隐患） | 会话只保留 agent（短时记忆）；LLM 客户端与 SQLite 连接**每轮在当前线程重建、轮末同线程关闭**；另加会话累计 token 统计 | 三轮对话全部 done，累计统计正确（2 次调用 / tokens 2143/11） |
| E13 | 模型把检索到的历史任务当成当前任务回答（"记住偏好"却回了 hello.txt 的完成报告） | 长期记忆注入系统提示词后，弱模型把"记忆里的示例"当成当前任务 | 记录为已知风险；缓解：任务描述更具体、预算/相关度控制注入条数、记忆库可手动删除干扰项 | 复现后通过"新会话 + 删除干扰记忆"验证行为恢复 |
| E14 | 相关性判断被弱词欺骗（生肖黄历页因命中"今年"被判为相关，导致自动重试不触发） | bigram token 含"今年/年的"等弱词，命中即算相关 | token 提取剔除弱词/虚词（今年/推荐/的/了…）；判相关改为"弱词过滤后命中 ≥1" | 单测 + 实测：原查询正确触发重搜 |
| E15 | 兜底查询的验收标准难定（严格 ≥2 命中会拒掉好结果；宽松 ≥1 又会放过"只命中地名"的百科页） | 泛词查询里"北京"这类地名 token 命中率高、区分度低 | 兜底结果改用**领域话题词**验收（实习→实习/招聘/岗位/校招），无领域配置时退回普通相关性 | 「北京实习」百科页被拒 → 继续尝试平台词前置查询 ✓ |

## 三、环境与工具链问题

| # | 问题 | 处理方式 |
| --- | --- | --- |
| T1 | GitHub 直连不通 | 用镜像（ghfast.top）克隆；推送走本地代理 `127.0.0.1:7890`，偶发失败重试 1–2 次即可 |
| T2 | 百度搜索触发"安全验证"、DuckDuckGo 超时 | 放弃这两个后端，只用 Bing（RSS）；在文档里如实说明后端限制与可选替换点 |
| T3 | PowerShell 内联 Python 被关键字/转义破坏（`end`、`\"`） | 改为写临时脚本文件再执行；用完即删 |
| T4 | Windows 与 Linux 命令差异（`for f in ...`、`diff -q` 报错） | 轨迹中可见模型自动改用 Python 完成同一任务——这也是"多工具冗余"的价值 |
| T5 | 控制台中文乱码（GBK） | 需要看中文输出时写 UTF-8 文件再读，或让脚本输出 ASCII 摘要 |
| T6 | HuggingFace 直连慢（向量检索依赖） | `HF_ENDPOINT=https://hf-mirror.com` 走镜像，模型缓存后离线可用 |
| T7 | 任务在临时目录执行，相对路径易错 | 每个任务独立 `mkdtemp` 工作目录，产物不污染仓库；脚本用 `sys.path` 自举保证可从任意位置运行 |
| T8 | 同一端口起了两个进程（旧 venv 残留 + 新 venv），请求可能落到旧代码 | Windows `SO_REUSEADDR` 允许重复绑定；多次重启未清理旧进程。排查方法：`Get-NetTCPConnection -LocalPort 8899 -State Listen` 看 PID 归属 → 清理为单实例 |
| T9 | 官网（fcbarcelona.com / ESPN）对 `http_get` 返回 403、JS 渲染页面抓不到正文 | 属反爬/前端渲染限制：如实标注"无法核实"；中长期改用 agent-native 搜索 API 的 `include_raw_content`（见 `docs/SEARCH_BACKENDS.md`） |

## 四、最值得在面试里讲的三条

1. **开放域任务失败的定位（U4 + E3/E4/E6）**：先做对照实验区分"任务难"还是"工具差"，再分三层修复
   （解析 → 结果 → 查询），最后加收口机制；结论是"检索质量 + 收口时机"比换更强模型更划算（成本 0、可离线回归）。
2. **资源预算的量化（U7 + U9）**：用 216 次扫描把"预算"和"步数"两个旋钮的敏感度分别量化
   （预算→跨会话任务 +25pt；步数→p95+2），再让模型自动选择 + 规则兜底 + 安全夹逼——把"拍脑袋默认值"变成有依据的默认值。
3. **静默失败类 bug（E7）**：异常被上层吞掉 → 功能"看起来在工作"（回退规则）而实际失效；
   修复不止于调用方，还把接口做成类型宽容 + 失败可见。这类问题在真实系统里最常见、也最容易漏测。
