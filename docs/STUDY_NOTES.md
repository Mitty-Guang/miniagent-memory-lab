# 源码精读与面试问答（miniagent 二次开发项目）

> 目标：能不看代码讲清楚整个项目——架构、关键文件、我的改动、设计取舍、局限。
> 面试官问“讲一个你熟悉的 Agent 项目”时，从这个文档里组织答案。

## 1. 一句话架构

MiniAgent 把 LLM 放进一个 `think → act` 的循环里：每步把「记忆中的消息 + 工具定义」
发给模型，模型要么返回工具调用（act 执行并把结果写回记忆），要么直接给最终回答（结束）。

```
用户输入
   │
   ▼
MiniAgent.run() ── while state == RUNNING and step < max_steps ──┐
   │                                                            │
   ├─ think(): llm.chat(memory.get_messages(), tools) ──┐       │
   │      ├─ 有 tool_calls → 存 assistant 消息 → act()  │       │
   │      └─ 无 tool_calls → FINISHED                   │       │
   │                                                    │       │
   └─ act(): 解析 arguments → tools.execute_tool() ──────┘       │
           → 结果写回 Memory（role=tool）────────────────────────┘
```

升级后的分层（2026-09-23，新增长期记忆 / HITL / tracing 后）：

```
任务文本 ──▶ 长期记忆检索（SQLite）──▶ 注入系统消息
                                     │
    ReAct 循环（think / act）◀───────┘
      ├─ 每步：短期记忆选择（固定预算）→ LLM
      └─ 工具调用 → HITL 审批 → 执行 → 结果回填
   结束：任务摘要写回长期记忆
（全程 tracing：LLM / 工具 / 审批事件 + token / 延迟）
```

## 2. 逐文件要点

### `schema.py`
- `Message`：role / content / tool_calls / tool_call_id 四个字段，用工厂方法构造；
- `Memory`：仅一个 `messages` 列表 + `get_messages()` 转 OpenAI 格式；
- `AgentState`：IDLE / RUNNING / FINISHED。

### `llm.py`
- `SimpleLLM.chat()`：拼 system prompt + 历史，`tools` 非空时带 `tool_choice="auto"`；
- 返回 `LLMResponse(content, tool_calls)`；
- **注意**：异常被 catch 后返回 `content="LLM调用失败: ..."`，调用方无法区分
  “模型答完了”和“调用失败了”——我后来在评测层用重试机制补上了这个洞。

### `tools.py`
- `BaseTool(ABC, BaseModel)`：name / description / parameters（JSON Schema），
  `to_function_def()` 转成 OpenAI 工具定义；
- 三个工具：`PythonExecutor`（exec）、`FileEditor`（read/write/list）、
  `BashExecutor`（subprocess shell=True, 30s 超时）；
- `ToolCollection`：注册表模式，`execute_tool(name, **kwargs)` 分发。

### `agent.py`
- `run()`：重置状态 → 用户消息入记忆 → 循环 think/act → 生成摘要；
- `think()`：调用 LLM，把 assistant 消息（含 tool_calls）写入记忆；
- `act()`：读取最后一条消息的 tool_calls，逐个执行，结果作为 tool 消息写回；
- `_generate_summary()`：从消息流里拼一个文本摘要。

## 3. 上游代码的优缺点（面试谈资）

**优点**
1. 极小且清晰：600 行把 ReAct 的骨架讲透了，没有框架黑盒；
2. 工具注册表 + JSON Schema 的设计是可扩展的（加工具=继承 BaseTool + 注册）；
3. LLM 层抽象干净，`base_url` 可换任意 OpenAI 兼容服务。

**缺点（也是我的改造点）**
1. `Memory` 无预算、无选择：长任务必然上下文膨胀，上游没有任何裁剪/压缩机制；
2. API 异常被吞：失败表现为“模型不调用工具”，静默提前结束；
3. `PythonExecutor` 用 `exec`、`BashExecutor` 用 `shell=True`，**无沙箱或白名单**
   （生产环境必须容器化 + 权限控制，这是上线前必须解决的安全问题）；
4. 没有可观测性：无 token 统计、无调用计数、无日志结构化；
5. 没有评测：`test_mini.py` 只测工具，不测 Agent 行为质量。

## 4. 我的二次开发：设计与取舍

### 4.1 为什么用“字符数”当预算代理？
引入 tiktoken 需要额外依赖且中英文混排估算偏差大；字符数与真实 token 数在
“选择哪条消息”这个粒度上单调性足够，评测结论不受影响。取舍：不可跨模型精确比较，
但本轮实验只用同一个模型，协议可控。

### 4.2 为什么用 leave-one-out 干预测“决策影响”？
- 与我的 memcausal 研究一致：相关性≠因果贡献；
- 相比 attention 权重等归因：干预是**行为级**证据，不依赖模型内部实现；
- 代价可控：每条记忆一次 LLM 调用（只重放最终回答，不重跑工具）；
- 局限：只测“删除单条”的边际效应，组合效应需要成对删除；答案相似度用启发式
  （文本二元组 + 数字一致性），不是 LLM Judge——换来可复现性，牺牲语义细腻度。

### 4.3 为什么 impact 权重取 0.4/0.2/0.4？
先验来自离线干预（强信号）、相关性来自文本匹配（弱信号但便宜）、近因是保底。
这是工程折中，不是调参最优；在小任务集上也不值得做大规模搜索。诚实地说：
**这个权重是我按先验强度拍的**，面试可以主动讲这一点，并给出“如何用验证集调”的方案。

### 4.4 踩过的坑：工具调用组的“原子性”
记忆裁剪类系统最容易踩的坑，而且分两层：

1. **孤儿 tool 消息**：删掉一条 assistant 的 `tool_calls` 消息后，它的 tool 结果消息
   失去前置引用，接口直接 400；
2. **不完整的工具调用组**（更隐蔽）：assistant 一次发了两个 tool_calls，
   只保住其中一个响应时，DeepSeek 官方 API 报
   `insufficient tool messages following tool_calls message`——之前用 opencode Zen
   网关时没触发，换成官方 API 后才暴露，说明不同网关的校验严格程度不同。

解决（两层防线）：
- **选择层原子化**：`message_groups()` 把 assistant(tool_calls)+其全部 tool 响应
  切成一个组，整组进/整组出，从源头避免拆散；
- **修复层兜底**：`repair_orphans()` 按组校验，组内缺任一响应就整组丢弃；
  干预实验（删单条）会拆散组，此时该组按“删除整个动作+观察”处理——这其实更符合
  记忆干预的语义（动作与观察是不可分的单位）。

### 4.5 踩过的坑：冷启动首个请求失败
新进程的第一次 LLM 调用有概率失败（超时/网络），而上游把异常吞成一条文本，
表现为“任务 1 步完成、成功率 0%”，一次浪费 144 秒。解决：`scripts/run_experiments.py`
启动时先做一次预热调用（warmup），并给失败调用加可见的指数退避重试日志。

### 4.6 踩过的坑：失败样本污染统计
干预实验中，如果某次反事实调用失败，答案相似度会算出接近 0，从而把该条记忆的
“影响”虚报成 1.0。解决：给干预结果加 `failed` 标记并从先验聚合中剔除；
全量运行本身失败的任务直接跳过分析。

### 4.5 踩过的坑：静默失败
网关超时的那段时间，所有任务“1 步完成、成功率 0%”——因为上游把异常吞成
一条 assistant 文本。解决：`CountingLLM` 检测 `LLM调用失败` 前缀并指数退避重试
（最多 5 次），评测脚本任务间加间隔。

### 4.6 怎么保证评测公平？
同任务集、同模型、同解码参数、同最大步数；三个受预算策略共享同一字符预算
（默认 500），`all` 不裁剪作为上界；判分全部确定性（文件内容/关键数字），
不用 LLM Judge；原始结果 JSON 落盘可审计。

### 4.7 长期记忆的设计取舍

- 为什么用 SQLite 而不是向量库？部署零依赖、可复现、跨进程持久化；检索用字符二元组
  Jaccard（与短期选择同口径），避免引入 embedding 模型带来的下载与偏差；要上真实场景时，
  这个位置替换为向量检索即可（接口不变）。
- 为什么"写摘要"而不是"写原始轨迹"？对应 CAIM 的发现——原始轨迹大量冗余；摘要
  （任务 + 结果）信息密度更高。代价是信息有损，这也是可讨论的取舍。
- 为什么检索要"排除当前会话"？保证测的是真正的跨会话记忆，而不是把当前会话内容读回来。

### 4.8 跨会话任务怎么判分？

两个阶段各自是独立会话（新 Agent + 新 session_id），共享同一个长期记忆库；
phase 1 只要求"确认记住"（教学），phase 2 才是真正的使用检验（文件内容 / 数值检查）。
成功 = 两个阶段都通过——测的是"写 → 读 → 用"的完整链路。

### 4.9 HITL 与 tracing 的设计取舍

- HITL：拒绝时回填结构化原因（而不是抛异常），让模型自适应改用其他工具——demo 里
  bash 被拒后模型改用 file_editor 完成同一任务；
- tracing：只记事件（LLM / 工具 / 审批）+ token / 延迟，不记完整 prompt（隐私与体积）；
  批跑默认关闭落盘，避免 200+ 次运行产生大量文件。

## 5. 面试模拟 Q&A（针对本项目）

**Q1：这个项目你做了哪些部分？**
上游是一个 190 星的 ReAct 教学框架；我做了部署适配、固定预算记忆选择模块、
离线决策影响分析与评测框架，并用它对比了四种记忆策略。上游代码基本没动，
新增逻辑全部以兼容接口的方式接入。

**Q2：为什么要做记忆选择？**
Agent 每步都把全部历史塞进上下文，长任务会：① 超上下文窗口；② 成本线性增长；
③ 关键信息被稀释（lost in the middle）。所以要在固定预算下决定“留什么、删什么”。

**Q3：你的选择策略怎么设计的？**
三种受预算策略（近因/相关性/决策影响）+ 全量对照。影响策略用 0.4×相关性 +
0.2×近因 + 0.4×离线干预测得的决策影响先验；必保任务定义和最新状态；
tool 消息做完备性修复。

**Q4：决策影响是怎么测的？**
leave-one-out：删掉一条记忆后用剩余历史让模型重答最终问题，
`impact = 1 - 答案相似度`。按“角色+是否含数字”聚合为类型先验。

**Q5：为什么不用 LLM 打分做相似度？**
可复现性和成本。启发式（二元组 + 数字一致）在同协议下足以区分“答案没变/变了”，
而且不需要额外调用；如果要写论文会换成 LLM Judge + 人工抽检。

**Q6：结果说明了什么？**（按实际实验结果回答，见 SECONDARY_DEV.md 第 5 节）

**Q7：tie-break：如果 impact 策略没赢过 relevance 怎么办？**
如实说结论：在 6 个小任务上没有显著优势，原因是任务太短、记忆压力不足；
下一步要延长任务（更多工具调用）、扩大任务集、做多预算曲线（预算越小差距越明显）。
这本身是“发现评测场景不匹配”的有效结论，说明我理解实验设计。

**Q8：这个框架能上生产吗？**
不能直接上。缺沙箱（exec/shell 无限制）、无权限控制、无 token 计量、无追踪、
无并发控制；补这些是工程化的工作量，也是我下一步想学的方向。

**Q9：和 LangChain/LangGraph 比差在哪？**
它是教学最小实现：单 Agent、无线程/记忆持久化、无中断恢复、无流式。
LangGraph 用显式的 State/Node/Edge 建模循环，并提供 checkpointer 与 interrupt，
我在另一个 demo 里实现过 ReAct + 多轮记忆 + 人工审批；两者对照能讲清楚
“框架原语帮你解决什么问题”。

**Q10：你从中学到了什么？**
① 记忆/上下文管理的第一性问题是“预算 + 选择 + 合法性约束”；
② 干预实验的坑（随机性、配对、缓存）比算法本身更影响结论可信度；
③ 评测框架比单次实验更值得投入——我的实验基础设施复用到了后续研究。

**Q11：长期记忆是怎么实现的？**
SQLite 存文本 / 会话 / 任务三类字段：read 用任务文本检索 Top-k 注入系统消息，
write 把「任务 + 结果」摘要落库；检索默认排除当前会话，保证测的是跨会话记忆。
短期（消息预算选择）与长期（库检索）是两层，分别对应上下文窗口与跨会话记忆。

**Q12：怎么验证长期记忆真的生效了？**
设计了 4 个跨会话任务（phase 1 教、phase 2 用）：例如 phase 1 记住"项目代号 ORION"，
phase 2 在新会话里创建包含该代号的文件。冒烟测试实测 ltm_rw=1/2（1 次读、2 次写）
且 phase 2 成功——写入确实被读取并用于决策。

**Q13：HITL 怎么做的？被拒绝会怎样？**
工具执行前走审批回调；拒绝时把结构化原因作为工具结果回填，模型会改用其他工具。
demo 实测：bash 被拒 → 改用 file_editor → 完成并自检。生产里这就是"危险操作人工把关"
的最小形态（后续可接 interrupt/审批流）。

**Q14：tracing 与成本统计怎么做的？**
LLM 层捕获 usage（prompt / completion tokens）与单次延迟；工具层记名称与成功与否；
审批层记放行 / 拒绝；事件可写 JSONL，summary 输出调用数 / token / 平均与最大延迟。
这些指标已进入评测表格（prompt token 列）。

**Q15：为什么做预算扫描而不是单点对比？**
单点（500 字符）只能说明"这个预算下的结果"；扫描 300 / 500 / 800 / 1200 能回答
"策略在预算紧 / 松时的差异"——也就是面试官爱问的"你的结论在什么条件下成立"。

**Q16：如果继续把它做成产品，下一步是什么？**
向量检索替换二元组、记忆冲突与时效管理（写策略）、多轮会话评测、MCP 工具生态、
沙箱与权限、tracing 接入看板；优先级按"能否支撑核心主张"和"真实业务约束"排。

**Q17：预算扫描发现了什么？**
216 次运行（18 任务 × 4 预算 × 3 策略）：整体成功率 93.1%，三种策略在 88.9%~100% 波动、
差异在噪声内——诚实结论是"这批确定性任务区分不出策略优劣"。两个有信号的点：
① **预算太紧反而更贵**（预算 300 时累计 token 最高，1200 时最低——预算紧导致更多重试步数）；
② **跨会话任务才是区分度所在**（recent 62.5% vs relevance/impact 81.3%）。

**Q18：多 Agent 对照的结论？**
Planner → Executor → Reviewer（失败带反馈重试）对比单 Agent：8 个任务上成功率都是 100%，
但多 Agent 的成本约为 2 倍（LLM 调用 3.5→7.1、token 2628→4508、耗时 3.35s→8.41s）。
结论：**多 Agent 不是免费的**——简单确定性任务上单 Agent 更优，多 Agent 的价值要在
更复杂/开放的任务上验证。这个"诚实负结果"本身就是面试加分项。

**Q19：可视化 GUI 怎么做的？**
零依赖：Python 标准库 HTTP 服务 + 原生 JS 轮询。页面实时展示 ReAct 轨迹、**本次上下文
选择**（选中/总条数与字符 vs 预算）、token/延迟、长期记忆读写、事件流与最终结果；
审批面板支持点击"批准/拒绝"（30 秒超时自动放行）。实现要点：给 BudgetedMemory 加
`last_selection` 探针；审批回调阻塞在工作线程里、由 HTTP 线程唤醒。

**Q20：LangGraph 版和手写循环什么关系？踩过什么坑？**
同一套记忆策略与工具，分别实现为手写循环和 StateGraph（memory → agent ⇄ tools）。
坑：把 `ToolNode` 包进自定义节点时忘记传 `config`，会抛
`ValueError: Missing required config key 'N/A'`——第一次工具调用就崩；修复是直接把它
作为节点使用，或在包装节点里显式透传 config。这个坑说明"框架原语不是包一层就行"。

**Q21：MCP 是怎么接的？**
把项目的沙箱工具（Python 执行 / 文件 / 命令）包成标准 **MCP Server**（stdio），
任何 MCP 客户端都能发现并调用；`client_demo.py` 演示了完整链路（列工具 → 调用 →
黑名单拦截生效）。依赖 mcp 2.x（FastMCP 已更名 MCPServer，踩过一次版本坑）。

**Q22：怎么在公开基准上验证的？**
接入了 **Mem2ActBench（ACL 2026）**：400 个"记忆驱动工具调用"任务（跨会话记住偏好 →
选对工具 + 填对参数）。简化协议：证据片段 + 40 条干扰 → 走本项目的记忆管线检索注入 →
原生 Function Calling 生成调用 → 判分 TA/参数 F1，并对比"无记忆"。
它同时也是我科研计划要接入的基准，工程与科研互相印证。

**Q23：还踩过哪些工程化的坑？**
① 工具调用组原子性（API 400，见 4.4）；② 冷启动首个请求失败（warmup + 退避，见 4.5）；
③ **失败样本污染**：网络抖动导致"LLM调用失败"被当成答案写进了长期记忆——已加守卫
（失败不写记忆）并收紧教学阶段判分；④ **监控面板口径错误**：一开始从 progress.log
"重建实验计划"，任务集从 18 变 21、日志混入多种运行后矩阵错位——改为以
`results/sweep_*.json`（权威结果）为准，日志只做"最近动态"。教训：**展示层不要自己
重建事实，读权威数据源**。

**Q24：联网工具怎么做的？安全上考虑了什么？**
两个工具：`web_search`（Bing 结果解析：标题/链接/摘要）与 `http_get`（公网文本抓取，
剥离脚本/标签、截断 4000 字符）。安全：
① **SSRF 防护**——拒绝内网/回环/链路本地/保留地址，且解析域名后逐个 IP 校验
（防 DNS 指向内网），scheme 限 http/https；
② 默认允许公网、可切白名单（`WEB_ACCESS=allowlist`）；
③ 与 HITL 审批配合（GUI 里可设"全部工具需审批"）。
一个实用教训：**搜索词要用简短关键词**——口语化长句会被搜索引擎切错（"今天 AI 领域
重要新闻"曾返回黄历），已在工具描述里给出用法规范，并在返回里提示"摘要通常已够作答"。

**Q25：搜索质量/收口问题是怎么定位和修的？**
现象：开放域任务（"下周去诺坎普看球，帮我规划路线"）连续失败，最后只回一句"抱歉"。
定位：拉轨迹 + 对照实验——同一引擎下短查询「诺坎普球场」3/3 稳定返回权威结果，而带
空格/后缀的「诺坎普球场 参观」返回"诺（汉字）_百度百科"（引擎对长短语分词错误）；
模型在劣质结果上反复检索、步数耗尽仍无答案。
修复分三层（都可离线单测）：
① 解析层：改用 Bing RSS（结构化、比 HTML 稳），HTML 解析兜底；
② 结果层：相关性过滤——中文 2-gram / 英文词匹配打分，剔除 0 分噪声并按相关度重排；
③ 查询层：整体不相关时自动剥离后缀词（参观/攻略/开放时间）缩短关键词重搜一次；
另加"预算感知收口"：剩余 2 步提示"停止检索、立即作答"，最后一步禁用工具调用，
摘要如实标注"步数耗尽未作答"。
复测：同任务同模型（20 步）→ 产出可执行的双场景方案 + 明确标注不确定项（官网 403）。
一句话：**失败原因常是"检索质量 + 收口时机"，工程修复比换更强模型更划算**。
